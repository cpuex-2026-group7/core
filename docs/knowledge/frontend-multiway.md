# Frontend の複数命令供給への拡張制約

調査日: 2026-11-12。「2-way」は 2 命令/cycle 以上の供給幅を指す。現行 RTL の静的調査に基づく制約と設計上の選択肢であり、複数命令版を実装・シミュレーションした結果ではない。

## 拡張時に決める必要がある契約

1. **フェッチ束の PC とメモリ帯域**
   - `src/frontend/frontend.sv:31,66,114` と `src/memory/i_mem.sv:25` は単一命令・単一読み出し。Queue の深さを増やしても供給幅は増えない。
   - ISA はワードアドレッシング（`src/defs/isa.sv:7`）。要求 PC から W 命令を読むなら、各命令は `P+i`、次の束は `P+W`。整列ブロック方式ならブロック境界と開始位置マスクが別途必要。redirect 先が束の途中でも、その命令から実行すること。
   - 束の次 PC と各命令の逐次 PC は別物。`br_decoder.sv:25,29` の命令単位の `PC+1`、分岐即値、JAL のリンク値を供給幅倍に変更しない。
2. **束内の分岐位置と予測の選択**
   - `frontend.sv:32,60,121,139,146` は BTB 応答・分岐種別・検査を各 1 件だけ保持。`btb.sv:33` は 1 PC を検索し、`frontend_defs.sv:2` の応答は valid/target だけで分岐位置を持たない。
   - `[通常命令@P, 分岐@P+1]` を毎 cycle 予測するには各位置の検索、またはブロックに分岐位置を保持する方式が必要。複数候補からプログラム順で最初に経路を変える分岐を選ぶ。選んだ命令の位置と PC を検査・BTB 更新まで対応させること。
   - 単一 BTB 更新ポートの継続使用は可能。ただし採用候補の更新を選ぶ、または更新を直列化する契約が必要。全候補の同時更新を必須としない。
3. **同じ束の後続命令の無効化**
   - `frontend.sv:39,56,101,160` は valid/fire を束内で区別せず、frontend redirect 時にも現在の F3 を Queue に投入する。現行で正しいのは F3 が 1 命令だから。
   - `[JAL@P, 通常命令@P+1]` から P+1 以外へ飛ぶとき、JAL は投入し、後続は除外する必要がある。cold redirect だけでなく warm BTB hit でも必要。F1/F2 の flush だけでは F3 の同じ束を除外できない。
   - 非分岐への BTB 誤 hit の修正でも、単純に束末尾へ進めると未処理の後続命令を飛ばす。再フェッチする範囲と投入済みの範囲を決め、欠落・重複を防ぐこと。レーンマスクまたは有効命令数などが必要。
4. **Queue の空き数と消費数**
   - `frontend.sv:19,50,155`、`fetchq.sv:10,24,27,30` は 1 push/1 pop。ready/valid は「1 件入る/1 件ある」の意味であり、2 件以上の保証ではない。
   - 命令単位の Queue なら、投入数以上の空き、読み出し可能数、受理数に応じた head/tail 更新が必要。空き 1 件に 2 件を投入しないこと。両 Queue は 1 スロットを空ける方式で、使用可能数は `2**IDX_WIDTH-1`。
   - 束単位の Queue も選べるが、分岐で短くなった束のマスクと、後段が 1 命令だけ受理した際の残りの保持が必要。残りと次の束を詰めて供給するかも帯域に影響する。
   - 全段共通 stall と束の一括受理は有効な設計。レーン別 stall は必須ではない。一部だけ受理するなら、F3 に残った命令を再投入しない仕組みが必要。
5. **命令と PC・予測・FTQ index の対応付け**
   - `frontend.sv:19,160,168` は命令だけを Fetch Queue に格納し、FTQ 割当て index も公開しない。`frontend_defs.sv:23` の FTQ データも PC/分岐種別のみ。
   - 後段は `src/defs/uop_types.sv:87` の `pc/predict_pc/ftq_idx` を要求する。`src/backend/ex/eu_0_int/fu_0/eu_0_fu_0_top.sv:109` と浮動小数点側は実 next PC と `predict_pc` を比較する。実際に採用した命令単位の予測 next PC を保持・搬送する契約が必要。束の次の要求 PC を全レーンの `predict_pc` に使わない。
   - 通常命令は FTQ に入らず、内部 redirect は外へ通知されないため、Fetch Queue 出力数を数えるだけでは命令 PC を一般に再構成できない。命令にメタデータを付けるか、束の base PC/位置/予測・割当て情報から再構成できる形式を定める。
   - この未実装は 1-way でも存在する。既存の `src/frontend/frontend_readme.md` 第 8 節の統合課題を、複数命令化の前提として扱う。
6. **FTQ の単位と分岐帯域**
   - `frontend.sv:168`、`ftq.sv:12,15,18,34,58` は「1 分岐 = 1 entry」、1 push/1 read/1 pop、復旧は原因分岐を残す `tail=restore_idx+1`。
   - 分岐単位を維持して複数分岐を同時受理するなら、分岐数の空き判定、順序付き複数割当てと命令への index 対応が必要。FTQ 参照・commit にも同時アクセス数に応じたポート、バッファまたは直列化が必要。1 分岐/cycle に制限する選択も可能で、その場合の停止条件を明示する。
   - 常時 taken の現構成では、最初の経路変更で束を打ち切れば後続の分岐は通常除外できる。したがって W 命令供給が無条件で W 分岐投入を要求するわけではない。ただし複数分岐の同時 commit は別の制約。
   - 束単位 FTQ へ変えるなら、entry 内の分岐位置、各命令の index/offset、同一 entry 内の若い分岐を除外する復旧規則が必要。entry 単位の現行 restore をそのまま流用しない。
7. **branch tag と同時 dispatch の依存関係**
   - frontend の tag 管理は TODO。backend は割当て済み tag/mask を受ける。割当て境界は [既存メモ](rob-brmask-boom.md) を参照。
   - 複数命令を dispatch する場合、同時の複数分岐には異なる tag を割り当て、同じ dispatch 群の後続命令には先行する未解決分岐の bit を含める。全レーンに同一の開始時 mask を配るだけでは依存を失う。割当て場所は frontend に限らず decode/rename でもよい。

## 拡張障害と区別する事項

- backend redirect は最古の復旧対象を選択した後の単一要求でよい。幅に合わせた複数 redirect 入力は必須ではない。Fetch Queue 全破棄も backend に残る古い命令を捨てることを意味しない。
- direct-mapped BTB の連想度、always-taken BPD、固定メモリレイテンシ自体は 2 命令供給を禁止しない。予測精度・将来のメモリ接続の問題と、供給幅のための必須変更を区別する。
- メモリをバンク化・広幅化しても、現 frontend が要求する 2 段の PC/命令/BTB 対応と stall 中の保持は維持するか、valid 制御ごと変更する必要がある。

## 検証と追加すべき観点

2026-11-12、現行ソースで `make -C test/frontend lint` と `make -C test/frontend BUILD_DIR=/tmp/core-frontend-multiway-audit test` が成功（300 checks）。複数命令動作は未検証。

拡張版の検証には、各レーンの分岐（cold/warm/誤 hit）、束の途中への redirect、束内後続の除外、Queue 残り 1 件、部分消費と再開、複数分岐の割当て・commit・復旧、index 折返し、各命令の PC/予測 next PC/tag/mask の対応が必要。
